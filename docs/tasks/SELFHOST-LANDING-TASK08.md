## 用户目标

把 TASK07 的一次性整理方法固化为可跨多个 GPT 对话重复执行的大批量流程。以后公司资料按批次发送，每个对话只处理一个有界批次；新对话通过仓库文档、私有总索引和批次卡恢复状态，不依赖旧聊天记录，最后再从已验收批次生成全量汇总。

## 本任务范围

1. 固定 13 列目标模板、模板摘要、规则包版本和变更原则。
2. 设计来源接收、只读固化、批次编号、批量上限、结构指纹、来源映射档案、标准化、异常复核、验收和汇总流程。
3. 设计机器可读的私有总索引及批次卡字段，定义跨对话开始、暂停、恢复和完成协议。
4. 明确临时汇总、已批准汇总与数据库导入包的边界，避免未经审核的数据静默进入正式库。
5. 提供项目负责人可直接复制到新对话的简短指令和每批交付清单。

## 明确排除

- 本任务不接收或整理新的业务文件，不生成新一批物料工作簿。
- 不把当前 TASK07 的文件专用解析器冒充为可处理任意公司表格的通用引擎。
- 不新增、修改或运行 Schema/Migration，不连接或写 PostgreSQL、SQLite、D1。
- 不 build、restart、deploy，不修改账号、权限、运行配置或业务数据。

## 验收标准

1. SOP 明确一批一任务、一批一对话、来源不变、输出可追溯、未知留空和人工批准边界。
2. 默认批次上限与超限拆分规则适合当前低资源服务器，并允许按实际文件调小。
3. 批次状态机、目录结构、文件命名、摘要、修订和幂等规则完整。
4. 新来源布局与已知布局区分清楚：已知结构可复用映射档案，未知结构必须先确认后成为新版本档案。
5. 批次卡模板足以让新对话恢复，无需引用旧聊天；业务文件和详细报告不进入 Git。
6. 最终全量汇总只读取通过机器校验且经人工批准的不可变批次版本；数据库导入另立任务。
7. 更新项目总控文档，完成文档一致性、敏感信息、资源和 Git 范围检查并创建独立提交。
