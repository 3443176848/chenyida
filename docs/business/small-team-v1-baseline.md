# 晨亿达 ERP 小团队 V1 业务基线

> 状态：`APPROVED BASELINE / HEADCOUNT VARIABLE / BUSINESS-FLOW FIRST / PRODUCTION NO-GO`
> 日期：2026-08-23（Asia/Shanghai）
> 决策：D-166、D-167
> 适用范围：少于20名内部用户的首期自托管 ERP；人数仅用于容量估算，不构成产品限制

## 1. 第一性原理

ERP 的首要任务不是拥有最多模块、页面或审批层，而是让全公司对同一笔业务事实达成一致，并能回答四个问题：

1. 现在发生了什么，权威记录在哪里。
2. 下一步由谁处理，需要什么输入。
3. 库存、数量、金额和状态是否守恒。
4. 发生错误时能否追溯、冲销和恢复。

因此 V1 按下列原则完成：

- 以跨岗位业务闭环验收，不以页面数、表数、Migration 数或代码量验收。
- 系统自动计算、校验和留痕；责任交接、定标、放行、过账和冲销仍由明确岗位确认。
- 人数变化只改变账号分配和容量，不改变业务规则，不触发代码分支或数据库结构变化。
- 少于20人只意味着部署和运维保持简单，不意味着放宽稳定ID、事务、权限、审计、幂等、并发、备份或冲销规则。
- 已有功能先证明能组成完整闭环；没有真实阻断前，不新增模块、表、角色或平台工具。

## 2. 岗位与容量假设

| 业务职能 | 现有角色代码 | 首期容量估算 | 主要责任 |
| --- | --- | ---: | --- |
| 管理/负责人 | `manager` | 2 | 经营看板、例外审批、跨部门协调 |
| 市场/销售 | `sales` | 2 | 客户、项目、报价、订单、交付跟踪 |
| 工程/项目 | `engineering` | 2 | 产品、BOM、工艺路线、工程交接与变更 |
| 计划/PMC | `planning` | 2 | 需求核算、缺料、采购申请、生产交接与进度 |
| 采购 | `purchase` | 2 | 供应商映射、询价、报价、定标、采购履约 |
| 仓库 | `warehouse` | 2 | 收货、批次、领退料、完工入库、发货与盘点 |
| 生产 | `production` | 2 | 工单、派工、报工、在制品和返工执行 |
| 品质 | `quality` | 2 | IQC、IPQC、FQC、不合格与放行 |
| 财务 | `finance` | 2 | 应收应付、收付款、冲销、项目资金与对账 |

合计18人只是当前规划参考。它不是最少人数、最大人数、许可证席位、并发上限、Seed数量或验收断言；任何岗位可以是1人、2人或更多人。`admin`与`operations`是系统治理职责，不自动形成额外业务部门或固定席位，可由后续实名账号方案按最小权限指定。

当前`app_users.role`没有每角色人数限制，技术上可为同一角色创建任意数量的受控账号；当前模型是每账号一个固定角色。如果实际名单出现一人兼多职，必须按最小权限另行确认复合职责方案，不能通过共享账号或给同一人复制多个账号规避审计。

## 3. V1 完成定义

只有同时满足下列结果，才可称为“小团队 V1 完成”：

- 每名实际员工使用独立账号，能够从自己的工作台完成获授权操作；停用、改密、重置和会话撤销可审计。
- 物料、客户、供应商、产品、BOM、工艺路线和单位具有稳定内部ID及有效状态，下游不以名称或外部料号作主键。
- 下列十条业务闭环使用同一版本源码和同一测试/UAT数据基线通过，关键交接没有手工补库或直接SQL。
- 库存Ledger与余额、批次、在制、采购/销售数量、应收应付和结算结果能够按来源对账。
- 错误通过退回、调整、冲销或反向记录处理，不原地改写已过账事实。
- 首期真实数据完成只读盘点、隔离试迁移、逐项核对和负责人确认。
- 员工UAT、可恢复备份、恢复演练、切换方案和明确上线授权全部完成。

## 4. 十条核心业务闭环

| 编号 | 业务闭环 | 主要交接 | V1最小输出 | 验收重点 |
| --- | --- | --- | --- | --- |
| ST-01 | 主数据建立与使用 | 采购/工程 → 审核人 → 全部门 | ACTIVE物料、客户、供应商、产品、BOM、Routing及供应商映射 | 一物一码、版本、单位、映射、审核、重复/冲突拦截，下游只引用稳定ID |
| ST-02 | 市场需求到工程接收 | 市场 → 工程 | 客户项目、需求版本、受控资料引用和接收/退回记录 | 项目编号稳定、版本不可覆盖、资料不泄露路径、交接有审计 |
| ST-03 | 工程方案到计划接收 | 工程 → 计划 | 产品版本、BOM版本、Routing及不可变Planning Package | 只允许有效版本；退回产生修订，不改写旧包 |
| ST-04 | 计划需求到采购/生产分流 | 计划 → 采购/生产 | 需求计划、库存/在途分配、采购申请和生产交接 | 数量守恒、缺料计算可解释、提交时重算；不自动创建RFQ、PO或工单 |
| ST-05 | 询价到采购订单 | 采购 → 供应商事实 → 采购确认 | RFQ、报价版本、比价、Award、PO和到货计划 | 固定Mapping、人工定标、非最低价原因、转单一次性、失败零半记录 |
| ST-06 | 到货到库存与应付 | 采购 → 仓库 → 品质 → 财务 | 收货、原料Lot、IQC、库存Ledger/Balance和AP来源/单据 | 不超收、批次追溯、未放行不得可用、收货与库存同事务、AP只消费一次 |
| ST-07 | 计划到完工入库 | 计划 → 生产 → 仓库 | 工单、BOM/Routing快照、预留、领退料、派工、报工、完工Lot | 不超领/超报/跳序，工序WIP守恒，RELEASED后快照不可改，冲销闭环 |
| ST-08 | 品质异常到处置/返工 | 品质 ↔ 生产/工程 | IQC/IPQC/FQC结果、缺陷、NCR、返工申请/执行或报废处置 | 检验来源稳定、放行额度不超量、处置与关闭分权、已消费放行不可重开 |
| ST-09 | 销售订单到出货与应收 | 市场 → 品质 → 仓库 → 财务 | 报价/销售单、成品分配、FQC、发货指令、Shipment和AR | 只发可用且已放行批次、不超订单/放行额度、出货与库存同事务、AR来源唯一 |
| ST-10 | 收付款、冲销与经营对账 | 财务 → 管理 | AP/AR结算、反向记录、项目资金和经营看板 | 金额按币种守恒、部分结算准确、已冲销不重复、报表能追到来源单据 |

身份、权限、审计、幂等、并发、备份和恢复是十条闭环共同的横切底线，不另建复杂平台。

## 5. 首期必需单据与报表

### 5.1 必需单据

- 主数据：物料卡、客户、供应商、供应商料号映射、产品版本、BOM版本、Routing版本。
- 市场/工程：客户项目、需求版本、受控资料引用、工程接收/退回、Planning Package。
- 计划/采购：需求计划、采购申请、RFQ、供应商报价、比价、Award、采购订单、到货计划。
- 仓库/生产：收货单、库存批次、库存流水、工单、领料/退料、派工、报工、完工入库、发货单。
- 品质：IQC、IPQC、FQC、缺陷、不合格、返工申请与处置记录。
- 财务：应付、应收、付款、收款、结算冲销及来源凭证。

### 5.2 必需报表

- 各岗位今日待办与逾期例外。
- 物料缺料、现有库存、正式预留、冻结量和有效在途。
- 未完成采购订单、待到货、待收货和供应商交付状态。
- 工单进度、在制品、待派工、待报工和待完工入库。
- IQC/IPQC/FQC待检、质量Hold、不合格和返工进度。
- 销售订单交付、待FQC、待发货和部分发货。
- 库存余额、Lot追溯、调整/冲销和账实核对。
- AP、AR、收付款、未结余额及按项目的净现金流；V1不把它称为完整会计利润。
- 管理看板及所有关键数字的来源下钻。

## 6. 首期数据范围

首期不追求把全部历史交易重演进新库，而采用“当前有效主数据 + 切换日可核对余额 + 未结事项 + 旧系统只读历史”的最小可验证策略：

1. 新建实名账号，不迁移旧密码或有效Session。
2. 迁移有效单位、客户、供应商、物料/别名/供应商映射、产品、已发布BOM/Routing和仓库位置。
3. 以可追溯Opening记录导入切换日库存及Lot、未结AP/AR和经负责人确认的期初事实。
4. 只迁移必须在新系统继续处理的未结项目、销售单、采购单和工单；已关闭历史保留在旧系统只读查询或受控归档中。
5. 每项导入保留旧标识、来源摘要、逐行结果和拒绝原因；重复、孤儿引用、数量/金额不平或状态不合法均不得自动猜测。

本节是试迁移范围基线，不授权读取、导出、修改或迁移真实数据。真实数据盘点、快照、试迁移和切换仍需单独明确授权。

## 8. 当前事实与真实缺口

- 自托管仓库已有11个技术角色、50个原生页面、37个一级业务/基础模块目录、233张表和46项Migration；核心业务Service已覆盖上述十条闭环的大部分对象。
- 当前人数没有写死；实际缺口不是“能否建立18个账号”，而是这些账号能否用同一版本完成真实跨岗闭环。
- 源码是alpha.47/0046，运行UAT仍是alpha.42/0040，不能把源码测试等同于当前员工可用状态。
- 既有UAT对市场→工程→计划→采购→PO及仓库收货预检有局部证据，但没有九个业务职能共同完成的完整员工UAT；生产、品质、出货和财务闭环也没有真实员工签收。
- 真实数据试迁移、未结事项核对、异机可恢复备份和正式切换均未完成。
- 当前账号模型每账号一个固定角色；若实际员工兼岗，需要真实名单后另行决定最小权限方案，不能先建设复杂角色平台。
